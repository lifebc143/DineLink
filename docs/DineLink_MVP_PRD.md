# DineLink 約飯 Web App MVP：產品需求規格

**版本：** 0.2 MVP  
**產品型態：** 手機優先的約飯／聚餐社交 Web App  
**目標架構：** Next.js App Router、PostgreSQL、Drizzle ORM、Google Maps

## 1. 產品定位

DineLink 將模糊的私訊邀約轉化為具備時間、地點、預算、買單方式與出席承諾的公開小型飯局。MVP 不以大量滑動或無止盡配對為目標，而以**清楚飯局規則、主辦人審核權、可追蹤出席紀錄與信用 rating**降低陌生社交的不確定性與爽約風險。

> 「下一餐，不只是吃飯。」DineLink 的最小可行承諾，是協助使用者在清楚條件與相互同意下，完成一場安心、準時且有互動品質的聚餐。

| 項目 | MVP 定義 |
| --- | --- |
| 主要使用者 | 想認識新朋友、但重視安全與約定感的都會成人。 |
| 核心行為 | 發起飯局、探索飯局、申請加入、主辦人審核、確認後聊天、完成出席與互評。 |
| 主要價值 | 用結構化飯局資訊取代猜測；用審核、取消規則、出席紀錄、互評與通知建立履約文化。 |
| 非目標 | 無限配對、公開交友牆、影音直播、匿名私訊，以及未驗證的金流代收。 |

## 2. MVP 核心功能模組

| 模組 | 使用者需求 | MVP 行為與驗收標準 |
| --- | --- | --- |
| 註冊與個人檔案 | 我想知道互動對象具備基本可辨識資料。 | 使用第三方登入或手機驗證建立帳號；檔案包含顯示名稱、頭像、性別、自介與驗證狀態。 |
| 飯局探索 | 我想快速找到時間、地點與預算合適的飯局。 | 卡片顯示主題、時間、餐廳、人數、買單方式與預算；可切換地圖並點選標記開啟詳情。 |
| 發起飯局 | 我想明確設定這頓飯的期待。 | 必填主題、時間、地點／餐廳、買單方式、預算與人數上限；保存 `placeId`、地址與座標。 |
| 申請與審核 | 我想在加入前表達動機，也讓主辦人掌握成員品質。 | **主辦人掌握成員審核權；申請狀態、取消規則與出席紀錄全程可追蹤。**申請狀態由 `pending` 轉為 `approved`、`rejected`、`withdrawn` 或 `cancelled`。 |
| 已確認聊天室 | 我只想與已確認赴約者溝通。 | 僅主辦人及 `confirmed` 出席者可讀寫群組訊息；未核准者請求聊天資料時回傳禁止存取。 |
| 出席與信用 rating | 我想累積可信任訊號，而非公開羞辱他人。 | 飯局完成後，主辦人或營運人員記錄出席、遲到、爽約；已出席成員可對同場成員各留一次準時、禮貌、趣味互評。信用摘要由服務端彙總，介面不得填入假資料或假評價。 |
| 通知 | 我不想錯過審核結果或飯局時間。 | 申請、核准、拒絕、取消、爽約、新訊息建立站內通知；開始前兩小時提醒已確認成員。 |

## 3. 主要使用流程

使用者在探索頁以飯局卡片或地圖標記開啟詳情，閱讀主辦人、時間、地點、買單方式、名額、取消規則與出席期望後送出申請。申請送出後，系統通知主辦人；主辦人接受時，申請者成為已確認成員並取得聊天室權限，拒絕或取消時則留下可追蹤的申請狀態與通知。飯局結束後，出席紀錄與同場互評由受控服務更新信用摘要。

詳細授權、狀態轉換與冪等性要求見 [`MVP_DATA_FLOWS.md`](./MVP_DATA_FLOWS.md)。

## 4. 商業模式設計

MVP 應先驗證「審核與出席信用是否提高完成率」，再逐步擴大付費機制。商業化不得干擾身份驗證、主辦人審核、取消規則與安全檢舉流程。

| 模式 | 階段 | 使用者價值 | 收益與治理 |
| --- | --- | --- | --- |
| Plus 訂閱 | Launch | 優先曝光、進階篩選、可視化飯局偏好。 | 月／季訂閱；不得販售信用分數或審核豁免。 |
| 點數方案 | Launch | 用於可選的體驗升級與合作活動。 | 僅於價值明確後導入，不影響申請與審核公平性。 |
| 特約餐廳 | Beta | 提供可預期的餐廳、套餐或場地選擇。 | 導流／預訂合作；需明確標示合作關係。 |
| 主題飯局置頂 | Launch | 協助主辦人觸及合適受眾。 | 保留廣告標示、頻次限制與風險審查。 |

## 5. 技術架構建議

正式產品建議以 Next.js App Router 作為全端 Web 基礎，將公開探索頁、登入後飯局流程與受保護 API 路由分層管理。[1] PostgreSQL 搭配 Drizzle ORM 能以型別化 schema 與 migration 管理關聯資料。[2]

| 層級 | 建議技術 | 職責 |
| --- | --- | --- |
| 前端 | Next.js App Router + TypeScript + Tailwind CSS + Lucide React | 手機優先畫面、Client Components 表單與地圖互動。 |
| 身份與授權 | OAuth／手機驗證服務 | 建立 `authSubject`，在每個寫入端點驗證當前使用者與資源擁有權。 |
| API | Route Handlers 或 Server Actions | 對飯局、申請、聊天、出席與評價執行輸入驗證、授權與 transaction。 |
| 資料與 API | **PostgreSQL + Drizzle ORM，將飯局、申請、聊天與評價拆分為獨立 Entity。** | 以 `dining_events`、`event_applications`、`chat_messages`、`event_reviews` 搭配出席與通知 Entity 管理狀態。 |
| 地圖 | Google Maps JavaScript API + Places | 地圖標記、地點選擇及地址預測；正式實作應限制回傳欄位以控制資料取用與成本。[3] |
| 儲存與通知 | 物件儲存服務 + 受管背景工作 | 儲存已授權的大頭照；執行兩小時提醒與可重試通知任務。 |
| 可觀測性 | 錯誤追蹤、結構化日誌與稽核事件 | 追蹤審核、取消、出席、爽約、信用更新與檢舉事件。 |

## 6. 信任、安全與隱私基線

| 風險 | MVP 控制措施 |
| --- | --- |
| 冒用與詐騙 | 驗證狀態、清楚檢舉入口、聊天室敏感交易警語與管理員稽核紀錄。 |
| 未核准存取 | 聊天、成員名單、審核與出席狀態均在服務端依所有權或 attendance 驗證。 |
| 取消與爽約爭議 | 保存取消、出席、爽約的原因、操作者與時間；提供人工覆核入口。 |
| 信用資料誤用 | 信用分數只由服務端彙總；禁止以付費購買評分、審核豁免或排名優勢。 |
| 個資處理 | 最小化公開欄位；精確地址與聯絡資訊依權限、時間與必要性揭露。 |

## 7. 0-to-1 Roadmap

| 階段 | 目標 | 主要產出 | 完成判準 |
| --- | --- | --- | --- |
| MVP | 建立可信任的飯局最小閉環。 | 帳號與實名驗證、飯局探索、申請審核、文字聊天室與基礎出席評價。 | 可形成一次端到端的發起、核准、聊天、出席與互評閉環。 |
| Beta | 驗證履約與餐廳合作價值。 | 出席率／信用評分系統、飯局前推播通知、餐廳合作方案。 | 可追蹤出席品質、改善提醒效率並驗證合作轉換。 |
| Launch | 驗證商業化與規模化營運。 | 訂閱制、點數方案、風險防護與營運後台。 | 商業化不降低公平性與安全性，營運能處理檢舉、取消與信用申訴。 |

## 8. MVP 成功指標

第一版應以「有品質的履約」優先於註冊量。建議追蹤：完整個人檔案率、已發布飯局的有效申請率、申請至核准時間、核准後聊天啟動率、飯局完成率、取消率、爽約率、信用 rating 覆蓋率、客服爭議率與回訪率。所有指標均應以去識別化、最小必要資料為原則處理。
